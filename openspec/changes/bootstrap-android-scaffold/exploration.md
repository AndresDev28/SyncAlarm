## Approaches

### A. Gradle DSL — Kotlin DSL vs Groovy DSL

1. **Kotlin DSL (`*.gradle.kts` + `libs.versions.toml`)**
   - Pros: Type-safe plugin DSL; same language as the rest of the codebase; version catalog gives one place to bump versions; plays well with `buildSrc`/convention plugins later.
   - Cons: Slightly more verbose than Groovy for trivial scripts; first-time compilation adds ~10s to clean builds (negligible after warmup).
   - Effort: Low. Matches Android Studio "new project" defaults since AGP 7+.

2. **Groovy DSL (`*.gradle` + no catalog)**
   - Pros: Shorter scripts; more Stack Overflow examples predate 2020.
   - Cons: No compile-time safety; string-typed version strings duplicated across modules; persona already defaults to modern conventions.
   - Effort: Low.

**Recommendation:** Kotlin DSL + `libs.versions.toml`. The `sdd-init` context already calls this out as assumed.

### B. Dependency Injection — Hilt vs Koin vs Manual

1. **Hilt** (Google/Dagger-based)
   - Pros: Compile-time DI graph; deepest Android integration (`@HiltAndroidApp`, `@AndroidEntryPoint`, `WorkerFactory` for `WorkManager`, `HiltWorker`); first-class with WorkManager + ViewModels.
   - Cons: KAPT/KSP overhead; steepest learning curve; annotations can leak into `:domain` if careless.
   - Effort: Medium to set up; Low to use daily.

2. **Koin**
   - Pros: Pure-Kotlin DSL; no annotation processor; lighter initial setup.
   - Cons: Runtime errors (graph resolution fails at first use, not at compile); weaker Android-specific lifecycle glue.
   - Effort: Low.

3. **Manual DI** (constructor injection + a tiny `ServiceLocator` object in `:app`)
   - Pros: Zero dependencies; easiest to teach; no codegen.
   - Cons: Doesn't scale beyond a handful of screens; harder to swap implementations for tests.
   - Effort: Lowest.

**Recommendation:** **Hilt** for `:app` and `:data`. `:domain` stays pure Kotlin with no DI annotations — repositories expose interfaces, and `:data` provides implementations through Hilt modules. Manual DI is an acceptable fallback if user prefers minimal dependencies.

### C. Test stack — JUnit 4 vs JUnit 5, MockK, Turbine, AssertJ/Kotest, Robolectric

1. **JUnit 5 (Jupiter) + MockK + Turbine + Kotest assertions**
   - Pros: Modern parameterized tests (`@ParameterizedTest` with `@MethodSource`); nested test classes; matches Android Studio Hedgehog+ default; MockK is Kotlin-first; Turbine is the de facto Flow test lib.
   - Cons: Android Gradle Plugin historically needed extra config; AGP 8.5+ works out of the box.
   - Effort: Low.

2. **JUnit 4 + Mockito-Kotlin + Truth**
   - Pros: Most Android tutorials still use it; widest community footprint.
   - Cons: Older API; Kotlin `runBlocking` boilerplate; Flow testing needs custom utilities.
   - Effort: Low.

3. **Robolectric** (for `:data` tests)
   - Pros: Lets `:data` unit tests run on JVM without an emulator.
   - Cons: Adds ~5MB to test runtime; can mask real Android lifecycle bugs.
   - Effort: Medium.

**Recommendation:** **JUnit 5 + MockK + Turbine + Kotest assertions** for `:domain` tests. **Robolectric** stays out of this scaffold (`:data` is a stub — no tests yet). Decision can flip to JUnit 4 if user has strong preference; either works.

### D. UI framework — Jetpack Compose vs XML/ViewBinding

1. **Jetpack Compose + Material 3**
   - Pros: Modern Android default; less boilerplate; declarative; better for Clean Architecture (`@Composable` renders `StateFlow` from `:domain`).
   - Cons: PRD doesn't specify; older team habits may favor XML.
   - Effort: Low.

2. **XML + ViewBinding**
   - Pros: Battle-tested; works with every Android library; easier to onboard beginners.
   - Cons: More boilerplate; harder to express reactive state.
   - Effort: Low.

**Recommendation:** **Jetpack Compose + Material 3**. `MainActivity` is a stub `setContent { MaterialTheme { Text("SyncAlarm") } }` — no real screen until a later change.

### E. Version catalog vs buildSrc vs convention plugins

1. **`libs.versions.toml` only**
   - Pros: Single file for versions; recommended by Android team since Gradle 7.4.
   - Cons: Still some duplication across module `build.gradle.kts` files (e.g. android {} block).
   - Effort: Lowest.

2. **`libs.versions.toml` + `buildSrc` with convention plugins**
   - Pros: Each module applies `id("sync.alarm.android.application")`; one place to configure Android defaults.
   - Cons: Heavier setup; pays off only after 3+ Android modules.
   - Effort: Medium.

**Recommendation:** **`libs.versions.toml` only**. Defer `buildSrc`/convention plugins until at least 4 Android modules exist (current count: 2 — `:app` + `:data`).

## Recommendation

Land a minimal but real Android scaffold that satisfies PRD §6's Clean Architecture + TDD-pure `:domain` contract and is small enough to fit the 400-line review budget. Specifically:

- **Build system:** Kotlin DSL + `libs.versions.toml`. AGP 8.5+, Kotlin 1.9.24, Gradle 8.7.
- **SDK targets:** `minSdk 26` (Android 8.0 — covers `EncryptedSharedPreferences`, modern `WorkManager`, `POST_NOTIFICATIONS` semantics, and ~95% device coverage), `compileSdk 34`, `targetSdk 34`. `jvmTarget 17` to match AGP 8+ default.
- **Package:** `com.syncalarm.app`.
- **Modules:** `:app` (Android application), `:domain` (pure Kotlin JVM, no Android), `:data` (Android library, stub).
- **DI:** Hilt in `:app` + `:data`; `:domain` stays framework-free.
- **UI:** Jetpack Compose + Material 3 in `:app` (single `MainActivity` stub).
- **Tests:** JUnit 5 + MockK + Turbine + Kotest assertions in `:domain` with one trivial `SanityTest`. Flips `openspec/config.yaml` `testing.strict_tdd` and `apply.tdd` to `true`.
- **Conventions:** `.gitignore`, `.editorconfig`, `commitlint.config.js` (or equivalent) for Conventional Commits, `AGENTS.md` for multi-agent guidance. (These are persona defaults — surface as a single user decision at propose time.)
- **No code in this scaffold beyond placeholders.** Real `:app` screens, `:data` repositories, `:domain` models/usecases belong to subsequent changes.

This recommendation maximizes architectural integrity for the smallest possible change footprint, leaving every meaningful product decision (rules engine, alarm scheduler, calendar sync, OAuth flow) to dedicated future changes.

## Risks

1. **DI choice has the largest blast radius.** Choosing Hilt vs Koin vs manual here dictates how every ViewModel, Worker, and Repository binds. Picking Koin to "keep it light" then discovering WorkManager needs Hilt's `HiltWorkerFactory` later means retrofitting across the codebase. Default to Hilt; surface this as an explicit user decision at propose time.
2. **UI framework (Compose vs XML) is the second-largest blast radius.** Compose's `@Composable` units map naturally to Clean Architecture state, but XML/ViewBinding is still mainstream in 2025–2026 enterprise shops. Default to Compose; surface as an explicit user decision.
3. **Strict TDD flip must land in this change, not later.** The PRD's "TDD-pure `:domain`" promise is hollow unless `strict_tdd: true` and an actual test runner are wired together. If user wants to defer the flip, that's fine — but it must be a deliberate decision, not an oversight. Surface at propose time.
4. **Gradle wrapper jar is a binary.** The 400-line review budget counts authored text; the wrapper jar is binary and does not count toward the budget. The orchestrator should know this before flagging PR size.
5. **No GitHub Actions / CI yet.** First PR will rely on local `./gradlew assembleDebug` and `./gradlew test`. CI can be a separate change (`bootstrap-android-ci`) so this scaffold stays under budget.
