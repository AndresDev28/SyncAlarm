## Approaches

### A. Workflow-file choice — pin to SHA vs major-version tag

1. **Major-version tags (the user's draft)**
   `actions/checkout@v4`, `actions/setup-java@v4`,
   `gradle/actions/setup-gradle@v4`, `github/codeql-action/init@v3`,
   `aquasecurity/trivy-action@master`, `android-actions/setup-android@v3`.
   - Pros: auto-receives bug fixes; readable; what every Android tutorial
     shows.
   - Cons: third-party actions can break or pivot; **`@master` is a
     floating ref** (no tag, no commit) — every run pulls a different
     action. Best practice (GitHub Hardening Guide, StepSecurity blog,
     OSSF Scorecard) is to pin third-party actions to a **commit SHA** so
     a compromised or yanked tag cannot silently change behaviour.
   - Effort: Low to write; Med to migrate to SHA later.

2. **SHA-pinned (with Dependabot auto-bumps)**
   `actions/checkout@<sha> # v4.x.y`, etc. Dependabot
   `version-updates` for `package-ecosystem: github-actions` keeps the SHA
   current.
   - Pros: supply-chain safety; auditable; matches the project's existing
     commitlint/Husky discipline.
   - Cons: SHAs are opaque to humans; reading the workflow needs the
     comment to know the version.
   - Effort: Low.

**Recommendation:** **SHA-pin all third-party actions and let Dependabot
keep them fresh.** The project already uses commitlint + Husky to gate
every commit, so SHA discipline is consistent with the existing posture.
Treat `@master` for trivy as a hard reject — pin to a release tag at
minimum.

### B. Trivy gating strategy — fail vs warn on first run

1. **`exit-code: "1"` on HIGH,CRITICAL (the user's draft)**
   - Pros: gates PRs on real findings; matches "secure-by-default" intent.
   - Cons: a fresh repo's transitive deps almost always have a few
     HIGH/CRITICAL findings. **First push will fail.** Owner must triage,
     then either fix or `ignore-unfixed: true` (filters out vulns with no
     fix yet — the median Android Gradle Plugin / Kotlin / Hilt transitive
     finding is in this bucket).
   - Effort: Low to enable; Med to triage the first run.

2. **Two-phase rollout**
   PR #1 lands the workflow with `exit-code: "0"` and
   `ignore-unfixed: true` (warning only — populates the Security tab
   without failing CI). PR #2 (after triage) flips to `exit-code: "1"`
   and trims `ignore-unfixed`.
   - Pros: zero risk of breaking `main`; surfaces findings without
     blocking merges.
   - Cons: two PRs instead of one; the project might never flip the gate
     if findings pile up.
   - Effort: Low-Med (two small PRs).

**Recommendation:** **Two-phase.** First PR ships warning-only (build
green, Security tab populated). Second PR tightens the gate after the
owner reviews the first batch. This honours the
`interactive + ask-on-risk` delivery strategy and protects `main` from
the very first scan.

### C. SDK provisioning on the CI runner

1. **Use `android-actions/setup-android@v3` (or `@v4`) and call
   `sdkmanager` for `platforms;android-35` and `build-tools;35.0.0`.**
   - Pros: official-ish, well-known, fine-grained control.
   - Cons: extra `sdkmanager` call adds 30–90s; action does not preinstall
     compileSdk platforms.

2. **Use the `gradle/actions/setup-gradle@v4` `android-components`
   add-on (if available) or hand-roll a `sdkmanager` step.**
   - Pros: fewer moving parts.
   - Cons: less idiomatic; harder to audit.

3. **Use a pre-baked Docker image (e.g. `cimg/android:2024.01.1`) and skip
   `android-actions/setup-android` entirely.**
   - Pros: fast; predictable.
   - Cons: ties the CI to a third-party image; out of step with the rest
     of the GitHub-Actions-native flow.

**Recommendation:** **Option 1.** `android-actions/setup-android@v4`
(per the upstream README: v4 is current, v3 works but is older) with an
explicit `sdkmanager "platforms;android-35" "build-tools;35.0.0"
"platform-tools"` step. Mirror the AGP/Kotlin/SDK versions from
`gradle/libs.versions.toml` into the workflow's `env:` block so a future
catalog bump surfaces here too.

### D. CodeQL build mode — manual vs autobuild vs none

The CodeQL docs explicitly state **`build-mode: none` is "not yet
supported for Swift, Go, or Kotlin"**. For Kotlin, the choice is
`build-mode: manual` (explicit `./gradlew :app:assembleDebug` between
`init` and `analyze`) or `build-mode: autobuild` (CodeQL's own
heuristics try to figure out the build).

**Recommendation:** **`build-mode: manual`** with an explicit build step.
The project's `:app:assembleDebug` is fast (Hilt + KSP warmup done) and
deterministic — exactly what CodeQL wants. `autobuild` can stumble on
Hilt's Gradle plugin transforms and is harder to debug.

### E. Workflow permission model

The user's draft puts `actions: read`, `contents: read`,
`security-events: write` at the top level. Per the GitHub Actions docs,
`actions: read` is the **default** — it does not need to be declared.
Setting it explicitly is harmless but noisy. `security-events: write` is
required for CodeQL to upload SARIF; `contents: read` is required for
`actions/checkout` and for private-repo CodeQL.

**Recommendation:** drop `actions: read`. Move the permissions block to
**job-level** (not workflow-level) so each job declares its own minimum
scope — defense in depth.

### F. One change vs two (CI + Security)

The user submitted one proposal with two workflow files. Should this be
one OpenSpec change or two?

**Recommendation:** **One change.** Both files are workflow YAML under
`.github/workflows/`, both depend on the same SDK/JDK/Gradle bootstrap,
both land in the same review, and the `bootstrap-android-ci` name in
`AGENTS.md` already covers the broader "CI infrastructure" scope. The
"two-phase Trivy" approach in Approach B is a separate concern — the
first phase can be a follow-up `tighten-trivy-gate` change after the
owner reviews the initial scan.

## Recommendation

Ship **one OpenSpec change** that adds the CI bootstrap and the security
scans, structured as a single PR with two workflow files plus minimal
spec touch-ups. The change is small enough to fit the 400-line review
budget when SHA-pinned (two YAML files + one Dependabot config + spec
edits ≈ 250 lines authored).

The workflow design:

- `.github/workflows/ci.yml`:
  - Triggers: `pull_request` (any branch), `push` to `main`,
    `workflow_dispatch`.
  - Concurrency: cancel-in-progress per `github.event.pull_request.number`
    or `github.ref`.
  - Top-level: `permissions: {}` (no implicit grants).
  - Job: `ubuntu-latest`, 25 min timeout (cold first run + KSP/Hilt
    warmup + Gradle download ≈ 8–12 min warm, ~15 min cold).
  - Steps: `actions/checkout@<sha>` → `actions/setup-java@v4` (temurin,
    17) → `gradle/actions/setup-gradle@v4` (auto-cache + config-cache) →
    `android-actions/setup-android@v4` (SDK base) → `sdkmanager
    "platforms;android-35" "build-tools;35.0.0"` (compileSdk match) →
    `./gradlew test --continue` → `./gradlew :app:assembleDebug`. Job
    permissions: `contents: read` only.
- `.github/workflows/security.yml`:
  - Triggers: `push` to `main`, `pull_request` to `main`, weekly cron
    `0 6 * * 1`, `workflow_dispatch`. **Do NOT add `pull_request` to
    Trivy** for the first cut (see Approach B two-phase).
  - Job 1 (`codeql`): `permissions: { contents: read, security-events: write }`,
    uses `github/codeql-action/init@v4` with `languages: java-kotlin`
    and `build-mode: manual` (NO `category: "/language:java-kotlin"` —
    see Risks R4); `analyze@v4` after a manual `./gradlew
    :app:assembleDebug` build step.
  - Job 2 (`trivy-fs`): `permissions: { contents: read, security-events: write }`
    (security-events only needed if Trivy is later wired to upload
    SARIF; can be dropped if not). Uses
    `aquasecurity/trivy-action@<release-tag-or-sha>` with `scan-type: fs`,
    `scan-ref: .`, `severity: HIGH,CRITICAL`, `ignore-unfixed: true`,
    `exit-code: "0"` on first phase (warning only — Security tab
    populated, no PR gate). **Drop `actions: read`** (it's the default).
  - `fail-fast: false` if jobs are ever put in a matrix later.
- `.github/dependabot.yml`: weekly bump for `gradle`, `github-actions`,
  `npm` (commitlint + Husky tooling).

Forward-compat (NOT in this change, but designed for):

- The CI job's `runs-on: ubuntu-latest` is the same target the future
  `reactivecircus/android-emulator-runner@v2` job needs. Adding an
  `instrumented` job later is a one-job addition.
- The `gradle/actions/setup-gradle@v4` cache key includes the OS, so
  adding an emulator job that hits the same Gradle home reuses the
  warm cache.
- The `permissions:` blocks are job-level, so the future instrumented
  job can add `pull-requests: write` (for comment-on-failure) without
  touching the build job.
